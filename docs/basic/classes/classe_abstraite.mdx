# Pilier 3 — Abstraction

L'**abstraction** est le troisième pilier de la POO. Elle consiste à **cacher la
complexité interne** d'un système et à n'exposer que les opérations essentielles.
L'utilisateur d'une classe sait ce qu'elle fait, sans avoir besoin de savoir
comment elle le fait.

:::note Abstraction vs Encapsulation
Ces deux piliers sont souvent confondus, car ils visent tous deux à « cacher »
quelque chose.

- **L'encapsulation** cache les *données* et les détails d'implémentation d'un
  objet concret. Elle protège l'état interne.
- **L'abstraction** cache la *complexité* en définissant une interface commune.
  Elle spécifie *ce que* les classes doivent faire, sans dire *comment*.

En pratique, l'abstraction s'exprime par des **classes abstraites** et des
**interfaces** qui définissent un contrat que les sous-classes doivent respecter.
:::

## Le problème sans abstraction

Reprenons notre fil rouge. Nous avons `CompteEpargne` et `CompteCredit` qui
héritent de `CompteBancaire`. Si on veut calculer les intérêts de tous les
comptes, comment s'assurer que chaque type de compte implémente cette opération ?

Sans abstraction, rien n'empêche un développeur d'oublier d'implémenter la
méthode `calculer_interets` dans une nouvelle sous-classe. Le bug ne serait
découvert qu'à l'exécution.

## Classes abstraites avec `abc`

Python propose le module `abc` (*Abstract Base Classes*) pour définir des classes
abstraites. Une **méthode abstraite** est une méthode déclarée dans la classe
mère mais sans implémentation. Python **interdit d'instancier** une classe qui
contient des méthodes abstraites non implémentées.

```python
from abc import ABC, abstractmethod

class CompteBancaire(ABC):
    def __init__(self, titulaire, solde=0.0):
        self.titulaire = titulaire
        self._solde = solde

    @abstractmethod
    def calculer_interets(self) -> float:
        """Retourne le montant des intérêts pour ce type de compte."""
        pass

    def appliquer_interets(self):
        """Méthode concrète qui utilise la méthode abstraite."""
        interets = self.calculer_interets()
        self._solde += interets
        return interets

    def deposer(self, montant):
        self._solde += montant

    def __str__(self):
        return f"Compte({self.titulaire}, {self._solde:.2f} $)"
```

```python
# On ne peut plus instancier CompteBancaire directement
c = CompteBancaire("Alice")  # TypeError : Can't instantiate abstract class
```

Les sous-classes **doivent** implémenter toutes les méthodes abstraites :

```python
class CompteEpargne(CompteBancaire):
    def __init__(self, titulaire, solde=0.0, taux=0.02):
        super().__init__(titulaire, solde)
        self.taux = taux

    def calculer_interets(self) -> float:   # obligation remplie
        return self._solde * self.taux


class CompteCredit(CompteBancaire):
    def __init__(self, titulaire, limite=1000.0):
        super().__init__(titulaire, 0.0)
        self.limite = limite

    def calculer_interets(self) -> float:   # obligation remplie
        # Les intérêts sont négatifs pour un compte en négatif
        if self._solde < 0:
            return self._solde * 0.18
        return 0.0


# Si on oublie calculer_interets :
class CompteInvalide(CompteBancaire):
    pass

c = CompteInvalide("Test")  # TypeError — calculer_interets non implémentée
```

## Les interfaces

Une **interface** est une classe abstraite dont **toutes** les méthodes sont
abstraites. Elle ne contient ni attribut, ni implémentation — seulement un
**contrat** que les classes qui l'implémentent doivent respecter.

Python n'a pas de mot-clé `interface` (contrairement à Java). On simule ce
concept avec `ABC` et uniquement des `@abstractmethod` :

```python
from abc import ABC, abstractmethod

class Exportable(ABC):
    """Interface : tout objet exportable doit pouvoir se convertir en dict."""

    @abstractmethod
    def to_dict(self) -> dict:
        pass

    @abstractmethod
    def from_dict(self, donnees: dict) -> None:
        pass


class CompteEpargne(CompteBancaire, Exportable):
    def __init__(self, titulaire, solde=0.0, taux=0.02):
        super().__init__(titulaire, solde)
        self.taux = taux

    def calculer_interets(self) -> float:
        return self._solde * self.taux

    def to_dict(self) -> dict:
        return {"titulaire": self.titulaire, "solde": self._solde, "taux": self.taux}

    def from_dict(self, donnees: dict) -> None:
        self.titulaire = donnees["titulaire"]
        self._solde    = donnees["solde"]
        self.taux      = donnees["taux"]
```

## Attributs abstraits

On peut forcer les sous-classes à définir un **attribut** (pas seulement une
méthode) en combinant `@property` et `@abstractmethod` :

```python
from abc import ABC, abstractmethod

class CompteBancaire(ABC):
    def __init__(self, titulaire, solde=0.0):
        self.titulaire = titulaire
        self._solde = solde

    @property
    @abstractmethod
    def type_compte(self) -> str:
        """Chaque sous-classe doit déclarer son type."""
        pass

    @abstractmethod
    def calculer_interets(self) -> float:
        pass

    def __str__(self):
        return f"[{self.type_compte}] {self.titulaire} — {self._solde:.2f} $"


class CompteEpargne(CompteBancaire):
    def __init__(self, titulaire, solde=0.0, taux=0.02):
        super().__init__(titulaire, solde)
        self.taux = taux

    @property
    def type_compte(self) -> str:
        return "Épargne"

    def calculer_interets(self) -> float:
        return self._solde * self.taux


c = CompteEpargne("Alice", 1000)
print(c)  # [Épargne] Alice — 1000.00 $
```

## Classes partiellement abstraites

Une classe abstraite peut contenir à la fois des **méthodes concrètes** (avec
implémentation) et des **méthodes abstraites**. Les méthodes concrètes offrent un
comportement par défaut réutilisable ; les méthodes abstraites imposent que les
sous-classes complètent ce qui est spécifique à chaque type.

C'est ce qu'illustre la méthode `appliquer_interets` ci-dessus : elle est
concrète et réutilisable par toutes les sous-classes, mais elle s'appuie sur
`calculer_interets`, qui elle est abstraite. Ce patron de conception s'appelle
la **méthode gabarit** (*Template Method*).

```python
# appliquer_interets est concrète — logique commune à tous les comptes
# calculer_interets est abstraite — logique spécifique à chaque type

epargne = CompteEpargne("Alice", 1000, taux=0.05)
interets = epargne.appliquer_interets()
print(f"Intérêts : {interets:.2f} $")  # Intérêts : 50.00 $
print(epargne)                          # [Épargne] Alice — 1050.00 $
```
