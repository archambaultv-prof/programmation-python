# Pilier 4 — Polymorphisme

Le **polymorphisme** (du grec *plusieurs formes*) est le quatrième pilier de la
POO. Il désigne la capacité d'une **même signature de méthode** à produire des
comportements différents selon le type de l'objet sur lequel elle est appelée.
Plusieurs classes peuvent ainsi partager la même signature tout en fournissant
chacune leur propre implémentation.

**Pourquoi c'est utile ?**
- On peut écrire du code générique qui manipule des objets de types différents
  sans connaître leur type exact.
- Ajouter un nouveau type de compte ne nécessite pas de modifier le code qui
  l'utilise — il suffit qu'il respecte l'interface.

## Surcharge de méthodes (*overriding*)

La forme la plus courante de polymorphisme en Python est la **redéfinition**
(*override*) d'une méthode héritée. La classe fille fournit sa propre
implémentation, qui remplace celle de la classe mère.

Reprenons notre fil rouge : `CompteEpargne` et `CompteCredit` implémentent
chacun `calculer_interets` à leur façon.

```python
from abc import ABC, abstractmethod

class CompteBancaire(ABC):
    def __init__(self, titulaire, solde=0.0):
        self.titulaire = titulaire
        self._solde = solde

    @abstractmethod
    def calculer_interets(self) -> float:
        pass

    def appliquer_interets(self):
        self._solde += self.calculer_interets()

    def __str__(self):
        return f"{self.titulaire} — {self._solde:.2f} $"


class CompteEpargne(CompteBancaire):
    def __init__(self, titulaire, solde=0.0, taux=0.02):
        super().__init__(titulaire, solde)
        self.taux = taux

    def calculer_interets(self) -> float:
        return self._solde * self.taux   # intérêts positifs


class CompteCredit(CompteBancaire):
    def __init__(self, titulaire, limite=1000.0):
        super().__init__(titulaire, 0.0)
        self.limite = limite

    def calculer_interets(self) -> float:
        if self._solde < 0:
            return self._solde * 0.18    # frais si découvert
        return 0.0
```

Le polymorphisme se révèle quand on traite une collection d'objets de types
différents de façon **uniforme** :

```python
comptes = [
    CompteEpargne("Alice", 5000, taux=0.05),
    CompteCredit("Bob", limite=2000),
    CompteEpargne("Charlie", 1200, taux=0.03),
]

# On appelle la même méthode sur tous les comptes —
# chacun répond à sa propre façon
for compte in comptes:
    compte.appliquer_interets()
    print(compte)

# Alice — 5250.00 $
# Bob   — 0.00 $     (pas de découvert, pas de frais)
# Charlie — 1236.00 $
```

## Extension de méthodes avec `super()`

Plutôt que de **remplacer** complètement une méthode de la classe mère, on peut
l'**étendre** : appeler la version de la classe mère et y ajouter un comportement.

```python
class CompteEpargneNotifiable(CompteEpargne):
    def appliquer_interets(self):
        interets = self.calculer_interets()
        super().appliquer_interets()          # comportement de la classe mère
        print(f"[{self.titulaire}] Intérêts de {interets:.2f} $ appliqués.")

c = CompteEpargneNotifiable("Alice", 1000, taux=0.05)
c.appliquer_interets()
# [Alice] Intérêts de 50.00 $ appliqués.
```

## Polymorphisme et typage canard

Python permet une forme de polymorphisme encore plus souple : le **typage canard**
(*duck typing*). Son nom vient de l'expression : *« Si ça marche comme un canard
et que ça fait coin-coin, c'est un canard. »*

Python ne vérifie pas le **type** d'un objet avant d'appeler une méthode. Il
vérifie seulement si l'objet **possède** la méthode demandée. Il n'est donc pas
nécessaire d'hériter d'une classe commune pour bénéficier du polymorphisme.

```python
class RapportPDF:
    def generer(self):
        print("Génération d'un rapport PDF...")

class RapportCSV:
    def generer(self):
        print("Export CSV des données...")

class RapportEmail:
    def generer(self):
        print("Envoi du rapport par email...")

# Aucun lien d'héritage entre ces trois classes —
# le typage canard fonctionne quand même
rapports = [RapportPDF(), RapportCSV(), RapportEmail()]
for r in rapports:
    r.generer()
```

### Quand utiliser le typage canard ?

Le typage canard est utile notamment quand vous interagissez avec des objets
issus de bibliothèques tierces que vous ne contrôlez pas. Vous ne pouvez pas
les faire hériter de votre classe abstraite, mais s'ils ont la bonne méthode,
ça fonctionne.

Cependant, pour les hiérarchies que vous maîtrisez, il est **recommandé** de
définir une classe abstraite (`ABC`) plutôt que de compter sur le typage canard :

- La classe abstraite documente explicitement le contrat.
- Python lève une erreur à l'instanciation si une méthode est oubliée, plutôt
  qu'à l'exécution quand la méthode est appelée.
- Le code est plus lisible et plus sûr.

| | Polymorphisme par héritage | Typage canard |
|---|---|---|
| Lien requis | Héritage d'une classe commune | Aucun |
| Vérification | À la conception | À l'exécution |
| Sécurité | Élevée (erreur tôt) | Faible (erreur tardive) |
| Recommandé pour | Hiérarchies maîtrisées | Interagir avec du code tiers |
